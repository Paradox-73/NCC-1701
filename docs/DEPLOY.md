# Deploying Subspace

Three free services, one per part:

| Part | Host | Why there |
|---|---|---|
| Client (React build) | **Vercel** | static files on a CDN, a preview URL for every pull request |
| Server + embedded simulator | **Render** (free web service, Docker) | needs a long-running Node process with WebSockets, which Vercel's serverless functions cannot keep open |
| Database | **MongoDB Atlas** (M0, 512 MB) | time-series collections, free |

Order matters: database first, then the server (it needs the database URL), then the client (it needs the server URL), then point the server's CORS back at the client.

## 1. MongoDB Atlas

1. cloud.mongodb.com → create a free **M0** cluster (any region near the Render region).
2. **Database Access** → add a user with a generated password.
3. **Network Access** → add `0.0.0.0/0` (Render's free tier has no fixed outbound IP).
4. **Connect → Drivers** → copy the string and put the database name in it:
   `mongodb+srv://<user>:<password>@<cluster>.mongodb.net/subspace?retryWrites=true&w=majority`

## 2. Render (server)

1. dashboard.render.com → **New → Blueprint** → pick this repository. Render reads `render.yaml`.
2. It asks for the two `sync: false` values:
   - `MONGO_URI`: the Atlas string from step 1.
   - `CORS_ORIGIN`: put `https://placeholder.invalid` for now, fixed in step 4.
3. Apply. The first Docker build takes a few minutes. Check `https://<service>.onrender.com/api/health` returns `{"ok":true,"mongo":"connected"}`.

`JWT_SECRET` and `DEVICE_KEY` are generated by Render. The server refuses to start in production with the example values.

## 3. Vercel (client)

1. vercel.com → **Add New → Project** → import this repository. Keep the **root directory at the repository root**: the client imports the `shared` workspace, and `vercel.json` already sets the install, build and output.
2. **Environment Variables** → `VITE_API_URL` = the Render URL (`https://<service>.onrender.com`, no trailing slash), for Production and Preview.
3. Deploy. Note the URL (`https://<project>.vercel.app`).

## 4. Connect them

1. Render → the service → **Environment** → `CORS_ORIGIN` = the Vercel URL (comma-separate several, for example a custom domain too). Save; Render redeploys.
2. GitHub → **Settings → Secrets and variables → Actions → Variables** → `SERVER_URL` = the Render URL. This turns on `keepalive.yml`, which stops the free service from sleeping.
3. Open the Vercel URL, sign in as `captain` / `ncc-captain`, check the top bar says **Live** and the readings move.

Vercel preview deployments get their own URLs, which are not in `CORS_ORIGIN`, so previews can show the UI but not sign in. Add a preview URL to `CORS_ORIGIN` when one needs testing against the real server.

## CI/CD

```
pull request ──▶ GitHub Actions ci.yml ──▶ tests (shared, server with MongoDB, client)
             │                         └─▶ client build, server Docker build
             └─▶ Vercel preview deployment (a URL on the PR)

merge to main ──▶ ci.yml again ──▶ checks pass ──▶ Render deploys the server (autoDeployTrigger: checksPass)
              └─▶ Vercel production deployment of the client
```

- **CI** (`.github/workflows/ci.yml`): every pull request and push to main runs `npm test` against a MongoDB 8 service container, builds the client as Vercel does and builds `server/Dockerfile` as Render does. A broken build shows on the PR before it is merged.
- **CD, server:** Render auto-deploys main only when every GitHub check on the commit passed, so a red CI run never reaches the hosted server.
- **CD, client:** Vercel's GitHub integration deploys every push: previews for pull requests, production for main. It does not wait for CI by itself. Two ways to make it wait, if needed: turn on branch protection (below) so nothing red reaches main, or Vercel → Settings → Git → **Ignored Build Step** with a script that checks the commit status.
- **Branch protection** (recommended, repo admin): GitHub → Settings → Branches → rule for `main` → require a pull request and the status checks `test` and `server-image`. Then main is always green, and both hosts only ever deploy green commits.
- **Keep-alive** (`.github/workflows/keepalive.yml`): pings `/api/health` every 10 minutes once `SERVER_URL` is set.
- **Rollback:** Render → Deploys → pick an earlier deploy → Rollback. Vercel → Deployments → an earlier one → Promote to Production. Or revert the commit on main and let the pipeline redeploy.
